# 码道开发剧本（分阶段 Prompt）

> 用法：**按顺序**把每一段粘进码道，等它跑完、你验收之后再进下一段。
> 一次给一大段需求，码道会写歪；分七段，每段都能验收，留痕也好看。

---

## 开工前：三件事

1. 码道工程目录就是 `E:\huawei`（本项目根目录，不要打开整个用户目录）
2. 开一个 git 仓库，**每完成一段就 commit 一次**，commit message 写你这段的 Prompt 摘要
3. 码道设置里把「自动批准」的编辑权限打开，但**浏览器/终端操作建议保留人工确认**

## 第 1 段：项目骨架 + 数据模型 + 剧本校验

**目标**：能把 JSON 读进来并通过 7 条校验，不写任何 LLM 逻辑。

```
在 project/ 下创建一个 Python 项目骨架，要求：

1. 技术栈：Python 3.11 + FastAPI + pydantic，不用 LangChain/LangGraph，
   不用 ORM，存储用标准库 sqlite3 或直接内存对象。
2. 目录结构：
   app/{main.py,config.py,models.py,script_loader.py}
   app/engine/{__init__.py}
   data/scripts/  data/regression/
   tests/
3. app/models.py 用 pydantic 定义 Fact / Role / Clue / Script / GameState，
   字段严格按我给的 JSON 结构，不做任何增减。
4. app/script_loader.py 实现 load_script(path) -> Script，并执行以下校验，
   任一失败抛 ValueError 且错误信息要说清是哪条 fact 哪个字段：
   - culprit 必须是合法 role id
   - solution_path 每条 fact 必须存在，且 holders 非空
   - relations / belief / source_of_error / clues.from 引用的 id 必须存在
   - 每个 role 至少持有 5 条 fact
   - 凶手必须持有 solution_path 中至少 2 条
   - 存在 belief 时 source_of_error 必填
5. tests/test_script_loader.py 写 3 个用例：正常加载、缺字段、凶手不持有线索。
6. 提供一个 CLI：python -m app.script_loader data/scripts/mistvale-inn.json
   成功时打印角色数/事实数/线索数和每个人的持有数。

不要写任何 LLM 调用，不要写前端。
```

**验收**：`pytest` 三个用例全绿；CLI 能打印出 5 个角色、23 条事实、8 条线索。
**留痕**：这一步的对话里有完整的 schema 讨论，**导出留着**，答辩时能证明"数据先行"。

## 第 2 段：意图解析 + 知识检索

**目标**：给定问题和 NPC，返回"这个人可能提到的 fact 列表"。

```
在 app/engine/ 下实现两个模块，纯函数，不调用 LLM：

1. intent.py
   parse_intent(question: str) -> Intent
   Intent 包含 topic: list[str]（time/weapon/motive/relation/event）、
   about_npc: str|None、keywords: list[str]。
   用规则优先：维护 TOPIC_RULES 字典（关键词 -> topic），
   命中即归类；一个都没命中时 topic 返回 ["event"]。
   注意中文分词不要引入 jieba 依赖，用关键词 in question 做包含匹配即可。

2. retrieval.py
   retrieve(npc: Role, intent: Intent, script: Script) -> list[Fact]
   规则：只返回 holders 包含 npc.id 的 fact；
   topic 与 intent.topic 有交集；按 (topic 命中数, sensitivity 降序) 排序；
   最多返回 3 条。为空时返回 []（由上层处理成"不知道"）。

3. tests/test_intent.py + tests/test_retrieval.py
   至少覆盖：问时间能命中 time 类 fact；
   问 r4 关于凶器的问题返回空（因为 r4 不持有 weapon 类 fact）；
   排序结果稳定。

这是知识边界的实现，必须保证"不持有就绝对检索不到"。
```

**验收**：单测覆盖"越权检索必须返回空"。
**留痕**：这段最能体现"知识边界"的设计思路，务必保留对话。

## 第 3 段：应答决策（三层真相）

**目标**：决定这个 NPC 是直说、回避还是撒谎。

```
实现 app/engine/policy.py：

1. effective_risk(fact, role) -> float
   = fact.sensitivity * (0.5 + role.lie_propensity)

2. threshold(role, state) -> float
   = clamp(0.9 - 0.5*role.lie_propensity - 0.4*state.pressure.get(role.id,0), 0.1, 0.95)

3. decide(fact, role, state) -> Decision
   Decision = {action: "disclose"|"evade"|"lie", view: str}
   逻辑：
   - 若 role.id in fact.belief：view 取 belief 里的错误版本，action 固定 "disclose"
     （他真诚地相信这个错误版本，所以他会说出来，且不记为撒谎）
   - 否则若 effective_risk < threshold*0.6：action="disclose"，view=fact.text
   - 否则若 effective_risk < threshold：action="evade"，view=""
   - 否则 action="lie"，view 由 LLM 生成假版本（先留 TODO 返回占位串）

4. 撒谎记录：action=="lie" 时写入 state.lies[role.id][fact.id] = view

写 tests/test_policy.py：
- 低敏感 fact 一定 disclose
- 凶手对 f04（sensitivity 1.0）一定 lie
- 提高 pressure 后，同一条 fact 从 lie 变成 evade（这就是"松口"）
- belief 污染时 action 必须是 disclose（不能记成撒谎）

pressure 机制是本作唯一的操作感，测试必须覆盖。
```

**验收**：第 3 条测试通过 —— 施压后从撒谎变成回避。
**留痕**：这段是"三层真相"落地的关键，截图存进 `proof/`。

## 第 4 段：自然语言生成 + 一致性校验

**目标**：把 Decision 变成人话，并保证前后不矛盾。

```
实现 app/engine/composer.py 和 app/engine/verifier.py，以及 app/llm.py。

1. llm.py：封装华为云 MaaS 的 chat completions，
   读环境变量 MAAS_API_KEY / MAAS_ENDPOINT / MAAS_MODEL，
   超时 20s，失败重试 1 次，再失败抛 LLMUnavailable。
   同时提供 mock 模式：环境变量 MOCK_LLM=1 时返回固定文案，方便无网调试。

2. composer.py：
   compose(role, decisions, intent, state) -> str
   system prompt 要求：以第一人称、口语、民国口吻回答，不超过 80 字，
   不复述问题，不说"根据我的记忆"这种旁白腔；
   action=evade 时表现为含糊其辞、转移话题；
   action=lie 时把 view 说得自然可信，不要明显心虚。
   必须把"角色名 + secret + goal"注入 system prompt，但 secret 不能直接说出口。

3. verifier.py：
   verify(draft, role, state) -> (final_text, ok)
   把 draft 抽出断言，与 state.lies[role.id] 和 state.testimonies 中同 fact 的历史说法比对；
   矛盾则带"必须与以下说法保持一致：…"重新生成，最多 2 次；
   仍矛盾则降级为模板句式（"那晚的事我记不太清了"）。
   最后把本次断言追加进 state.testimonies。

4. tests：用 MOCK_LLM=1 跑通全链路，断言 verifier 在人为制造矛盾时会触发重写。

注意：verifier 里的"抽断言"先用简单的关键词 + fact 文本相似度，
不要引入额外的 LLM 调用，否则延迟会翻倍。
```

**验收**：连续问同一个 NPC 同一个问题 5 次，答案语义一致。
**留痕**：**这一段一定要录屏**，因为它是"一致性"这个卖点的唯一证据。

## 第 5 段：API + 局状态机

**目标**：能通过 HTTP 玩完整一局。

```
实现 app/game.py 和 app/main.py：

1. GameState 加：round、pressure(dict)、testimonies(list)、lies(dict)、clues(list)、ended(bool)
2. 接口：
   POST /api/game                      -> 开局，返回 opening + 5 个角色 public 信息
   POST /api/game/{gid}/ask            -> {npc_id, text}，SSE 流式返回
   POST /api/game/{gid}/present        -> {npc_id, clue_id}，pressure += 0.25（上限1.0）
                                          并让 NPC 重新回答一次
   GET  /api/game/{gid}/state          -> 线索、压力、轮次
   POST /api/game/{gid}/accuse         -> {npc_id}，返回结算：是否命中、真相时间线、玩家漏掉的 fact
3. SSE 事件：event: token / event: meta（含 clue_unlocked、pressure）/ event: done
4. NPC 说出某条 fact 时，若该 fact 有对应 clue，自动解锁并放进 state.clues
5. 一局存在内存 dict 里即可，key 用 uuid，不做持久化

要求：所有接口加 /health；异常统一返回 {code, message}，不要裸 500。
```

**验收**：用 curl 或 Apifox 走完 开局→提问→出示→指认 全流程。
**留痕**：把接口调试成功的截图存进 `proof/`。

## 第 6 段：前端三栏

**目标**：一屏放下，能玩。

```
在 web/ 下写原生 HTML+JS（不要引入构建工具），三栏布局：

左栏 嫌疑人列表：5 张卡片，显示姓名、公开身份、压力条、已获线索数；
      点击选中，选中态明显。
中栏 对话流：玩家消息靠右，NPC 消息靠左带角色名；
      NPC 回复用打字机逐字显示（消费 SSE token 事件）；
      底部输入框 + 发送按钮，回车发送。
右栏 线索板：已解锁线索做成卡片；点击卡片出现「出示给…」按钮，
      选中 NPC 后调用 /present；出示过的卡片变灰。

视觉要求：
- 民国/悬疑氛围，深色背景 + 暖黄文字，衬线字体优先
- 线索板要有"物证"的质感（边框、阴影），它是在告诉评委"这是游戏不是聊天"
- 不要做动画库，CSS transition 足够

结算页：全屏遮罩，左侧真相时间线逐条亮起（1.5s 一条），
右侧列出玩家已获得的 fact 和漏掉的 fact（漏掉的高亮）。
底部一个「再玩一局」按钮。
```

**验收**：不看代码，纯用鼠标能玩完一局。
**留痕**：截 3 张图 —— 主界面、对话中、结算页。这三张直接进 PPT。

## 第 7 段：回归测试 + 部署

**目标**：可复现，能上线。

```
1. data/regression/questions.json 放 30 条用例，格式：
   {npc, q, expect_contain|expect_not_contain|expect_change_after_pressure}

   真实模式失败时打印实际回答，方便人工判断。

4. 写 deploy.md：ECS 上从零到跑起来的完整步骤（含 Nginx 反代和 systemd 配置）。
5. 加 Dockerfile（可选但建议，评委复现会加分）。
```

**留痕**：把测试通过截图存 `proof/`，标注"30 条一致性回归"。
