# 剧本 Schema 与编写规范

> 剧本是**数据**，不是代码。引擎不改，换一份 JSON 就是另一个本子。

---

## 1. 顶层结构

```jsonc
{
  "id": "mistvale-inn",          // 唯一标识
  "title": "雾镇旅馆",
  "version": "1.0",
  "era": "1937 年冬",             // 用于开场氛围
  "opening": "……",                // 开场旁白，200 字以内
  "victim": { "id": "v0", "name": "陈守义", "desc": "…" },
  "culprit": "r1",                // 真凶 role id
  "solution_path": ["f05","f06","f08","f15","f16"],  // 最小破案链
  "roles": [ … ],
  "facts": [ … ],
  "clues": [ … ]
}
```

---

## 2. roles

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✓ | `r1`…`r5` |
| `name` | string | ✓ | 角色名 |
| `public` | string | ✓ | 公开身份，玩家一开始就能看到 |
| `secret` | string | ✓ | 核心秘密，**引擎不会直接说出口**，只用于判断敏感度 |
| `goal` | string | ✓ | 行为目标，决定撒谎方向 |
| `lie_propensity` | 0~1 | ✓ | 撒谎倾向，越高越容易编瞎话 |
| `alibi` | string | ✓ | 默认口供，被问到"你在哪"时的第一反应 |
| `relations` | object | ✓ | `npc_id -> {type, trust}`，`trust` 0~1 |
| `is_culprit` | bool | | 与顶层 `culprit` 一致，便于引擎快速判断 |

**编写要点**：`secret` 和 `goal` 必须是**具体的、能被追问的**。写"我有不可告人的秘密"没有用，要写"我挪用了三百大洋"。

---

## 3. facts（核心）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✓ | `f01`… |
| `text` | string | ✓ | **客观事实**，一句话，不带评论 |
| `topic` | string[] | ✓ | `time` / `weapon` / `motive` / `relation` / `event`，用于检索 |
| `holders` | string[] | ✓ | **谁知道这条**。这个字段就是知识边界 |
| `sensitivity` | 0~1 | ✓ | 说出这条对自己有多危险 |
| `belief` | object | | `npc_id -> 他相信的错误版本`（三层真相的第二层） |
| `source_of_error` | string | | 谁误导了他。**这是给玩家的隐藏线索** |

### 敏感度怎么定

| 分值 | 含义 | 例子 |
|---|---|---|
| 0.0–0.2 | 公开信息，说了没事 | 暴雪封路 |
| 0.3–0.5 | 说了有点麻烦 | 我看见谁上了楼 |
| 0.6–0.8 | 说了会被怀疑 | 我挪用了钱 |
| 0.9–1.0 | 说了就完了 | 人是我杀的 |

引擎实际判断时用的是：

```
effective_risk = sensitivity × (0.5 + lie_propensity)
```

所以同一条 fact，凶手觉得危险，老实人觉得还好。**这是"角色性格"落到数值上的地方。**

### 三层真相怎么写

```jsonc
{
  "id": "f03",
  "text": "争吵大约在 22:45 就停了",        // 客观事实
  "holders": ["r2"],
  "belief": { "r2": "那场争吵一直闹到 23:10 才停" },  // 他记错了
  "source_of_error": "r1"                              // 是沈玉兰让他记错的
}
```

玩家问周砚青"几点吵完的"，他会**真诚地回答 23:10**。他不知道自己在说错话。
玩家如果拿这个时间去对质沈玉兰，就会发现时间对不上 —— 这就是推理的钩子。

> 一个剧本里**至少要有 1 条** belief 污染，否则三层真相这套设计就白做了。

---

## 4. clues

线索是玩家能拿到手的卡片，**由 fact 派生**。

```jsonc
{ "id": "c01", "from": "f05", "name": "阿蘅的目击", "desc": "23:00，有人看见沈玉兰从书房出来，袖口有灰" }
```

| 字段 | 说明 |
|---|---|
| `from` | 来源 fact id。NPC 说出这条 fact 时，线索自动解锁 |
| `name` / `desc` | 卡片显示文案，比 `text` 更口语化 |

**线索数量建议 6–10 条**。太少玩家没得推，太多记不住。

---

## 5. 校验规则（写脚本时必过）

引擎启动时会跑以下检查，任一不过就拒绝加载：

1. `culprit` 必须是合法 role id
2. `solution_path` 里每条 fact 都必须存在，且**每条的 `holders` 里至少有一个人**（否则永远挖不出来）
3. `relations` / `belief` / `source_of_error` 引用的 id 必须存在
4. `clues.from` 必须指向存在的 fact
5. 每个 role 至少持有 5 条 fact（否则问什么都不知道，体验崩）
6. **凶手必须持有 `solution_path` 里的至少 2 条**（否则审不出东西）
7. 若存在 `belief`，`source_of_error` 必填

第 6 条最容易漏。凶手什么都不知道，玩家就无从下手。

---

## 6. 新增一个剧本的流程

1. 定死者、定凶手、定 5 个嫌疑人（每人一个秘密 + 一个动机）
2. 写时间线（整点级别，6–8 个节点）
3. 按时间线拆成 20–25 条 fact，逐条标 `holders` 和 `sensitivity`
4. 挑 1 条做 belief 污染
5. 从 fact 里挑 6–8 条派生 clues
6. 定 `solution_path`（4–6 条，必须能串成链）
7. 跑校验脚本

**一个人写一个本，最快 3 小时。** 不要在这个阶段追求文笔，先保证逻辑自洽。
